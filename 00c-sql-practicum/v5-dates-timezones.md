# В.5 Время и даты: часовые пояса, календари, сроки, когорты

## Зачем это аналитику

Половина споров «чей отчёт правильный» сводится ко времени: один считает сутки по UTC, другой по Москве, третий берёт дату оплаты вместо даты доставки. Аналитик, который пишет требования к отчёту, обязан зафиксировать пояс, событие и границы периода, иначе разработка выберет их сама. На собеседованиях время — любимая ловушка live-задач: «посчитайте заказы за вчера», «найдите дни без загрузки», «постройте когортную таблицу». Кандидат, который сразу спрашивает «в каком поясе сутки?» и не забывает про неполные когорты, выглядит на уровень старше.

## Что понять

- [ ] **`timestamptz` хранит момент** (внутри — UTC) и показывает его в поясе сессии (`TimeZone`); **`timestamp` без зоны** — «настенное время» без привязки к поясу.
- [ ] **`AT TIME ZONE` работает в обе стороны**: из `timestamptz` делает настенное время в поясе, из `timestamp` — момент. Направление определяется типом аргумента, а не намерением автора.
- [ ] **Граница суток зависит от пояса**: «заказы за 1 сентября» по UTC и по Москве — разные множества строк. Пояс отчёта — требование, а не деталь реализации.
- [ ] **`date_trunc('day', ts, 'Europe/Moscow')`** (PostgreSQL 12+) режет сутки в заданном поясе независимо от сессии.
- [ ] **Фильтр по дню — полуоткрытым диапазоном** `[начало; начало + 1 день)`, а не `::date =`: так работает индекс и нет вопроса о «23:59:59.999».
- [ ] **Длительность**: разность моментов — `interval`; в сутках — `extract(epoch FROM ...) / 86400`; `age()` возвращает календарные месяцы и годы, а не точную длительность.
- [ ] **Опоздание** = `delivered_at > promised_at`; NULL в сроке и ещё не доставленные заказы требуют явного правила, иначе доля «плывёт».
- [ ] **Календарь строится через `generate_series`**: отсутствие строк в данных находится только относительно ожидаемого календаря, а ожидаемый календарь — бизнес-правило.
- [ ] **Систематический сдвиг времени** между источниками находится распределением разницы по поставщикам.
- [ ] **Когорты**: активация и удержание по месяцу; последние когорты неполные, их ячейки нужно отсекать, а не показывать нулями.

### Что хранится и что показывается

`timestamptz` (timestamp with time zone) вопреки названию пояс не хранит. При записи значение переводится в UTC, при чтении — в пояс текущей сессии. Один и тот же заказ в двух сессиях:

```sql
SET TIME ZONE 'UTC';
SELECT id, created_at FROM orders WHERE id = 100000;
--  100000 | 2025-08-23 01:51:11.488904+00

SET TIME ZONE 'Europe/Moscow';
SELECT id, created_at FROM orders WHERE id = 100000;
--  100000 | 2025-08-23 04:51:11.488904+03
```

Момент тот же, изменилось только отображение. `timestamp` (without time zone) — просто «число на часах»: что записали, то и прочитаете, в любой сессии. Разницу видно, если записать одну строку `'2025-09-01 10:00'` в оба типа из двух разных сессий:

```sql
CREATE TEMP TABLE tz_demo (label text, wall timestamp, moment timestamptz);
SET TIME ZONE 'UTC';
INSERT INTO tz_demo VALUES ('вставлено в UTC', '2025-09-01 10:00', '2025-09-01 10:00');
SET TIME ZONE 'Europe/Moscow';
INSERT INTO tz_demo VALUES ('вставлено в Москве', '2025-09-01 10:00', '2025-09-01 10:00');
SET TIME ZONE 'UTC';
SELECT * FROM tz_demo;
```

```
       label        |        wall         |         moment
--------------------+---------------------+------------------------
 вставлено в UTC    | 2025-09-01 10:00:00 | 2025-09-01 10:00:00+00
 вставлено в Москве | 2025-09-01 10:00:00 | 2025-09-01 07:00:00+00
```

В `wall` две одинаковые строки, хотя это события, разнесённые на три часа. Восстановить, какое было раньше, уже нельзя. Отсюда правило для требований: **моменты событий храним в `timestamptz`**; `timestamp` уместен для «настенного» смысла — «магазин открывается в 10:00 по местному времени».

### AT TIME ZONE в обе стороны

Оператор `AT TIME ZONE` (есть в стандарте SQL; в MySQL похожую роль играет `CONVERT_TZ`) делает противоположные вещи в зависимости от типа слева:

```sql
SELECT timestamptz '2025-09-01 00:00' AT TIME ZONE 'Europe/Moscow';  -- 2025-09-01 03:00:00 (timestamp: сколько было на часах в Москве)
SELECT timestamp   '2025-09-01 00:00' AT TIME ZONE 'Europe/Moscow';  -- 2025-08-31 21:00:00+00 (timestamptz: момент московской полуночи)
```

Ошибиться направлением легко. Хотим границу «московских суток 1 сентября» и пишем:

```sql
-- НЕПРАВИЛЬНО: слева timestamptz, получаем 03:00 настенного времени,
-- которое сравнение снова трактует как 03:00 по поясу сессии (UTC)
SELECT count(*)
FROM orders
WHERE created_at >= (timestamptz '2025-09-01' AT TIME ZONE 'Europe/Moscow')
  AND created_at <  (timestamptz '2025-09-02' AT TIME ZONE 'Europe/Moscow');
-- 1039
```

Граница уехала на шесть часов от нужной (03:00 UTC вместо 21:00 UTC предыдущего дня), а число выглядит правдоподобно. Правильно — слева настенное время:

```sql
SELECT count(*)
FROM orders
WHERE created_at >= (timestamp '2025-09-01' AT TIME ZONE 'Europe/Moscow')
  AND created_at <  (timestamp '2025-09-02' AT TIME ZONE 'Europe/Moscow');
-- 1044
```

Короче и надёжнее — литерал со смещением: `timestamptz '2025-09-01 00:00+03'`. Для Москвы смещение постоянное, но для поясов с переходом на летнее время безопаснее имя пояса.

### Граница суток: заказы за 1 сентября

```sql
SELECT count(*) FILTER (WHERE created_at >= timestamptz '2025-09-01 00:00+00'
                          AND created_at <  timestamptz '2025-09-02 00:00+00') AS utc_day,
       count(*) FILTER (WHERE created_at >= timestamptz '2025-09-01 00:00+03'
                          AND created_at <  timestamptz '2025-09-02 00:00+03') AS msk_day
FROM orders;
```

```
 utc_day | msk_day
---------+---------
    1046 |    1044
```

Разница всего в два заказа, и это опаснее, чем кажется: множества строк разные. Московские сутки забирают около 135 заказов из вечера 31 августа по UTC и отдают около 137 заказов из последних трёх часов 1 сентября. По выручке те же сутки расходятся уже на 265 тысяч рублей (42,2 млн против 42,5 млн). Сверка «по дням» двух систем с разными поясами даёт расхождение каждый день, хотя итог за месяц почти совпадёт.

Правило для требований: **в описании отчёта всегда указан пояс, в котором считается день**, и он один на все показатели отчёта.

Для группировки по суткам в нужном поясе есть `date_trunc` с третьим аргументом (PostgreSQL 12+):

```sql
SELECT date_trunc('day', created_at, 'Europe/Moscow') AS msk_day, count(*)
FROM orders
WHERE created_at >= timestamptz '2025-09-01 00:00+03'
  AND created_at <  timestamptz '2025-09-03 00:00+03'
GROUP BY 1
ORDER BY 1;
```

```
        msk_day         | count
------------------------+-------
 2025-08-31 21:00:00+00 |  1044
 2025-09-01 21:00:00+00 |  1121
```

Результат — момент начала московских суток, показанный в UTC. Это не ошибка, а честное отображение: начало московского 1 сентября и есть 21:00 UTC 31 августа. Без третьего аргумента `date_trunc` и `::date` режут сутки по поясу сессии — тот же запрос даст разные ответы у коллеги с другим `TimeZone` в DBeaver.

### Фильтр по дню: диапазон, а не ::date

```sql
-- Работает, но плохо
WHERE created_at::date = date '2025-09-01'
-- Правильно
WHERE created_at >= timestamptz '2025-09-01' AND created_at < timestamptz '2025-09-01' + interval '1 day'
```

У первого варианта две проблемы. Приведение зависит от пояса сессии: в UTC — 1046 заказов, после `SET TIME ZONE 'Europe/Moscow'` тот же текст запроса возвращает 1044. И выражение над столбцом мешает индексу: на временном индексе по `created_at` первый запрос читает весь индекс с фильтром (оценка стоимости ~4350), второй — только нужный диапазон (~35). Подробно о планах — в [В.7](v7-query-performance.md). Полуоткрытый интервал `[начало; конец)` к тому же не требует писать `23:59:59.999` и не теряет последние микросекунды суток.

### Длительности: interval, epoch, age

Разность двух `timestamptz` — `interval`. Для отчётов его обычно переводят в часы или сутки через число секунд:

```sql
SELECT o.id,
       s.delivered_at - o.created_at AS lead_time,
       round(extract(epoch FROM s.delivered_at - o.created_at) / 86400, 2) AS lead_days
FROM orders o
JOIN shipments s ON s.order_id = o.id
WHERE o.id IN (100000, 100001, 100002);
```

```
   id   |       lead_time        | lead_days
--------+------------------------+-----------
 100001 | 1 day 11:36:12.455511  |      1.48
 100000 | 3 days 12:09:29.010221 |      3.51
 100002 | 7 days 04:50:44.870469 |      7.20
```

Две ловушки. `extract(day FROM interval '2 days 23 hours')` вернёт 2, а не 2,96: это поле «дни», а не длительность. И `avg()` над интервалами выдаёт формы вроде `1 day 31:56:02` — PostgreSQL не переносит часы в дни сам; для читаемого вида есть `justify_hours` (`50:00:00` → `2 days 02:00:00`), но для расчётов надёжнее epoch.

`age()` считает календарную разницу: `age('2025-03-31', '2025-01-31')` = `2 mons`, `age('2025-03-01', '2025-01-31')` = `1 mon 1 day`, хотя между этими датами 29 суток. Это удобно для «возраста в месяцах» и номера месяца жизни когорты, но не для SLA в часах.

### Сроки и опоздания

Бизнес-правило стенда: заказ опоздал, если `delivered_at > promised_at`. На всех доставленных:

```sql
SELECT count(*) AS delivered,
       count(*) FILTER (WHERE o.promised_at IS NULL) AS no_promise,
       round(100.0 * count(*) FILTER (WHERE s.delivered_at > o.promised_at) / count(*), 2) AS late_pct_all,
       round(100.0 * count(*) FILTER (WHERE s.delivered_at > o.promised_at) / count(o.promised_at), 2) AS late_pct_known
FROM orders o
JOIN shipments s ON s.order_id = o.id
WHERE s.delivered_at IS NOT NULL;
```

```
 delivered | no_promise | late_pct_all | late_pct_known
-----------+------------+--------------+----------------
    134050 |        555 |        14.98 |          15.04
```

Сравнение с NULL даёт NULL, такой заказ не попадает ни в опоздавшие, ни в вовремя. В знаменателе `count(*)` он есть, в `count(promised_at)` нет — отсюда две разные цифры. Обе можно защитить, но выбрать нужно осознанно и записать. Варианты: исключить заказы без срока и показать их число рядом; восстановить срок по правилу (`created_at + sla_days`), если бизнес согласен, что правило было тем же; считать их отдельной категорией «срок неизвестен». Все NULL здесь — канал `api` в апреле: это след старой версии интеграции, и такое наблюдение стоит вписать в требования.

Вторая ловушка — **недоставленные заказы**. Если считать долю опоздавших по неделе создания и только среди доставленных, последняя неделя выглядит прекрасно: у sftp-поставщиков 22% против обычных 33–36%. Дело не в улучшении, а в том, что долгие доставки ещё не завершились. Корректнее группировать по неделе срока (`promised_at`), брать только те заказы, срок которых уже наступил, и считать недоставленный к сроку заказ опоздавшим (задача 3).

### Календарь: чего нет в данных

GROUP BY не покажет дни, которых нет в таблице. Чтобы найти пропуски загрузки фида, нужен ожидаемый календарь, построенный `generate_series` (в других СУБД — рекурсивный CTE или таблица-календарь), и антисоединение с фактом:

```sql
WITH calendar AS (
    SELECT d::date AS day
    FROM generate_series(date '2025-04-01', date '2025-09-30', interval '1 day') AS d
),
loaded AS (
    SELECT DISTINCT supplier_id, loaded_at::date AS day
    FROM supplier_feed_loads
    WHERE status = 'OK'
)
SELECT s.id, s.integration_type, count(*) AS missing_days, min(c.day), max(c.day)
FROM suppliers s
CROSS JOIN calendar c
LEFT JOIN loaded l ON l.supplier_id = s.id AND l.day = c.day
WHERE s.is_active
  AND l.day IS NULL
GROUP BY s.id, s.integration_type
ORDER BY s.id;
```

```
 id | integration_type | missing_days |    min     |    max
----+------------------+--------------+------------+------------
 31 | sftp             |            5 | 2025-07-10 | 2025-07-14
 36 | manual           |           52 | 2025-04-05 | 2025-09-28
 37 | manual           |           52 | 2025-04-05 | 2025-09-28
 38 | manual           |           52 | 2025-04-05 | 2025-09-28
```

У ручных поставщиков «пропущено» 52 дня — ровно все субботы и воскресенья за полгода. Это не сбой: они грузят остатки только по будням. Значит, **ожидаемый календарь — бизнес-правило**, и его нужно спросить и записать, прежде чем писать алерт. После учёта правила (`extract(isodow FROM day) <= 5` для `manual`, где 6 и 7 — выходные) остаётся одна настоящая дыра — пять дней у поставщика 31 (задача 2). Именно в эти дни его заказы принимались по устаревшим остаткам, и неделя 14 июля в задаче 3 у sftp выделяется.

### Когда два источника расходятся на 3 часа

Время отгрузки есть в двух местах: `shipments.shipped_at` и событие `SHIPPED` в `order_status_history`. Если сравнить их «в лоб», расхождений тысячи и непонятно, откуда. Сильный приём — **распределение разницы**: сгруппировать по величине расхождения и посмотреть, кто в каждую группу попадает.

```sql
WITH hist_shipped AS (
    SELECT order_id, min(changed_at) AS shipped_at_hist   -- min: в журнале бывают дубли события
    FROM order_status_history
    WHERE status = 'SHIPPED'
    GROUP BY order_id
)
SELECT h.shipped_at_hist - s.shipped_at AS diff,
       count(*) AS orders,
       count(DISTINCT o.supplier_id) AS suppliers,
       min(o.supplier_id) AS supplier_example
FROM shipments s
JOIN hist_shipped h ON h.order_id = s.order_id
JOIN orders o ON o.id = s.order_id
GROUP BY 1
ORDER BY 2 DESC;
```

```
   diff    | orders | suppliers | supplier_example
-----------+--------+-----------+------------------
 00:00:00  | 132604 |        37 |                1
 -03:00:00 |   3672 |         1 |               33
```

Ровно −3 часа у всех заказов одного поставщика — почерк ошибки пояса: его система пишет московское время и помечает его как UTC. Случайные задержки дали бы размазанное распределение, а здесь одна точка. Последствия видны дальше по цепочке: около сотни заказов поставщика 33 по журналу «отгружены раньше оплаты», а отгрузки около полуночи попадают не в те сутки. Подробно этот кейс разбирается в [В.6](v6-reconciliation.md).

### Когорты: активация и удержание

**Когорта** (cohort) — группа клиентов, объединённых месяцем события: регистрации или первого заказа. Активация на стенде — первый заказ в течение 14 дней после регистрации. Наивный запрос по всем покупателям:

```sql
WITH first_order AS (
    SELECT customer_id, min(created_at) AS first_order_at
    FROM orders
    GROUP BY customer_id
)
SELECT date_trunc('month', c.registered_at)::date AS reg_month,
       count(*) AS registered,
       round(100.0 * count(*) FILTER (WHERE f.first_order_at < c.registered_at + interval '14 days')
             / count(*), 1) AS activation_pct
FROM customers c
LEFT JOIN first_order f ON f.customer_id = c.id
GROUP BY 1
ORDER BY 1;
```

```
 reg_month  | registered | activation_pct
------------+------------+----------------
 2025-01-01 |       2305 |            0.0
 2025-02-01 |       2019 |            0.0
 2025-03-01 |       2221 |           22.6
 2025-04-01 |       2268 |           62.8
 ...
 2025-08-01 |       2316 |           75.1
 2025-09-01 |       2197 |           64.6
```

Нули в январе — не провал маркетинга: заказы в базе начинаются с 1 апреля, у этих людей окно активации закрылось раньше, чем начались данные (**левая граница**). Провал сентября — тоже артефакт: у зарегистрировавшихся после 17 сентября 14 дней ещё не прошли (**правая граница, неполная когорта**). Правило отсечки: в когорту активации входит только тот, у кого окно целиком лежит внутри периода данных — `registered_at >= '2025-04-01'` и `registered_at + 14 дней <= '2025-10-01'`. Сентябрь после этого показывает около 76%, на уровне августа (75%) (задача 5).

Таблица удержания (retention): строки — месяц первого заказа, столбцы — номер месяца жизни, в ячейке — доля когорты, сделавшей заказ в этом месяце. Номер месяца считается из разницы лет и месяцев (или через `age()`); сводная собирается `max(...) FILTER (WHERE month_n = k)`, в стандартном SQL — `max(CASE WHEN month_n = k THEN ... END)`. Ключевая деталь — **ячейки, которые ещё не наступили, должны быть пустыми, а не нулями**. Наивная сводка показывает у августовской когорты `m2 = 0.0` и читается как «все ушли», хотя второй месяц жизни у неё — октябрь, которого нет в данных. Ещё одна оговорка: апрельская когорта (около 5900 человек против 1500–2000 у остальных) раздута теми, кто зарегистрировался до апреля и впервые попал в данные в апреле. Её стоит показывать с пометкой или строить когорты по месяцу регистрации (задача 6).

### Типичные ошибки

- `::date` и `date_trunc` без пояса в отчёте: ответ зависит от настроек клиента того, кто запускает запрос.
- `AT TIME ZONE` в неверную сторону: граница сдвигается на часы, число остаётся правдоподобным.
- Хранение моментов в `timestamp` без зоны: из двух источников с разными поясами уже не собрать порядок событий.
- Конец дня как `23:59:59` вместо полуоткрытого интервала.
- `extract(day FROM interval)` как «длительность в днях».
- Доля опоздавших без правила для NULL в сроке и для недоставленных: последняя неделя «улучшается» сама.
- Поиск пропусков через GROUP BY по факту: дней без строк в результате нет.
- Ожидаемый календарь «каждый день» для всех: выходные ручных поставщиков становятся ложными алертами.
- Неполные когорты, показанные нулями или включённые в средний процент.

### Как говорить об этом на собеседовании

На задачу «посчитайте заказы за вчера» начните с уточнений: в каком поясе сутки, по какому событию (создание, оплата, доставка), какие статусы. Затем — полуоткрытый интервал и упоминание индекса. На когорты: назовите определение (когорта по чему, событие активности по чему), скажите про неполные когорты и как вы их отсекаете. Если видите систематическое расхождение времени между источниками, предложите показать распределение разницы: «если это одна точка у одного источника, это пояс, а не задержка». Такой ход мысли ценится выше синтаксиса.

### Коротко

- `timestamptz` — момент, показанный в поясе сессии; `timestamp` — настенное время.
- `AT TIME ZONE` меняет тип: направление задаёт тип слева.
- Пояс суток — требование к отчёту; группировка по дню — `date_trunc('day', ts, 'пояс')`.
- Фильтр по дню — `>= начало AND < начало + 1 день`.
- Длительность — через epoch; `age()` — календарная.
- Опоздание: явное правило для NULL-срока и недоставленных, группировка по неделе срока.
- Пропуски ищутся против ожидаемого календаря, календарь — бизнес-правило.
- Сдвиг времени между источниками — распределение разницы.
- Когорты: отсекать неполные ячейки и помнить про левую границу данных.

### Задача 1. Заказы за 1 сентября по UTC и по Москве

Верните одной строкой число заказов и выручку (`sum(total_amount)`) за 1 сентября 2025 года по UTC и по московскому времени. Объясните, откуда разница и почему она мала по числу заказов, но заметна по деньгам. Таймер: 10 минут.

<details markdown="1">
<summary>Решение и разбор</summary>

```sql
SELECT count(*) FILTER (WHERE created_at >= timestamptz '2025-09-01 00:00+00'
                          AND created_at <  timestamptz '2025-09-02 00:00+00') AS utc_orders,
       count(*) FILTER (WHERE created_at >= timestamptz '2025-09-01 00:00+03'
                          AND created_at <  timestamptz '2025-09-02 00:00+03') AS msk_orders,
       sum(total_amount) FILTER (WHERE created_at >= timestamptz '2025-09-01 00:00+00'
                                   AND created_at <  timestamptz '2025-09-02 00:00+00') AS utc_revenue,
       sum(total_amount) FILTER (WHERE created_at >= timestamptz '2025-09-01 00:00+03'
                                   AND created_at <  timestamptz '2025-09-02 00:00+03') AS msk_revenue
FROM orders;
```

```
 utc_orders | msk_orders | utc_revenue | msk_revenue
------------+------------+-------------+-------------
       1046 |       1044 | 42215437.53 | 42480059.71
```

Сутки по Москве — это интервал с 21:00 UTC 31 августа по 21:00 UTC 1 сентября. Они забирают около 135 заказов из вечера 31 августа и теряют около 137 из позднего вечера 1 сентября. Число почти совпало случайно: заказы распределены по часам ровно, а вот суммы у разных заказов разные, поэтому выручка разошлась на 265 тыс. рублей. Вывод для сверок: близкие итоги не доказывают, что сравниваются одни и те же строки.

Проверьте, что `WHERE created_at::date = '2025-09-01'` даёт 1046 в сессии UTC и 1044 после `SET TIME ZONE 'Europe/Moscow'`. Один и тот же текст запроса, разные ответы.

`FILTER` есть в стандарте SQL, но поддерживается не везде; переносимый вариант — `count(CASE WHEN ... THEN 1 END)` и `sum(CASE WHEN ... THEN total_amount END)`.

### Задача 2. Дни без фида по активным поставщикам

Для каждого активного поставщика найдите дни с 1 апреля по 30 сентября, когда не было ни одной успешной (`status = 'OK'`) загрузки фида, с учётом правила: ручные поставщики (`integration_type = 'manual'`) грузят только по будням. Верните `supplier_id`, `day`. Таймер: 15 минут.

<details markdown="1">
<summary>Решение и разбор</summary>

```sql
WITH calendar AS (
    SELECT d::date AS day
    FROM generate_series(date '2025-04-01', date '2025-09-30', interval '1 day') AS d
),
expected AS (                       -- ожидаемый календарь — бизнес-правило
    SELECT s.id AS supplier_id, c.day
    FROM suppliers s
    CROSS JOIN calendar c
    WHERE s.is_active
      AND (s.integration_type <> 'manual' OR extract(isodow FROM c.day) <= 5)
),
loaded AS (
    SELECT DISTINCT supplier_id, loaded_at::date AS day
    FROM supplier_feed_loads
    WHERE status = 'OK'
)
SELECT e.supplier_id, e.day
FROM expected e
LEFT JOIN loaded l ON l.supplier_id = e.supplier_id AND l.day = e.day
WHERE l.supplier_id IS NULL
ORDER BY e.supplier_id, e.day;
```

```
 supplier_id |    day
-------------+------------
          31 | 2025-07-10
          31 | 2025-07-11
          31 | 2025-07-12
          31 | 2025-07-13
          31 | 2025-07-14
```

Ровно пять дней у поставщика 31. Без правила будних дней вы получите ещё по 52 «пропуска» у поставщиков 36–38 — все выходные. Ловушки: `dow` считает воскресенье нулём, `isodow` — семёркой, выходные по ISO — 6 и 7. Фильтр `status = 'OK'` важен: около 150 загрузок завершились ошибкой, но у каждой есть успешный повтор через час, так что в этот день фид всё же был. Загрузки идут в 03:00–04:50 UTC, поэтому `loaded_at::date` в UTC и по Москве совпадает; при других часах загрузки пришлось бы решать, к какому дню она относится.

Заметьте, что запрос не видит «пустые успешные» загрузки поставщика 33 — у них статус `OK`. Это тема урока В.6.

</details>

### Задача 3. Доля опоздавших по неделям: sftp против api

Постройте по неделям долю опоздавших заказов для поставщиков с интеграцией `sftp` и `api` (два столбца рядом). Решите сами, по какой неделе группировать и что делать с недоставленными, и обоснуйте. Таймер: 20 минут.

<details markdown="1">
<summary>Решение и разбор</summary>

Наивный вариант — неделя создания, только доставленные — даёт в последней полной неделе сентября у sftp около 22% вместо обычных 33–36%. Это **цензурирование** (censoring): заказы, которые доставят с опозданием, ещё в пути и в выборку не попали. Правильнее группировать по неделе срока `promised_at`, брать только заказы со сроком до «сейчас» и считать недоставленный к сроку заказ опоздавшим:

```sql
WITH due AS (                       -- заказы, у которых срок уже наступил
    SELECT sp.integration_type,
           date_trunc('week', o.promised_at)::date AS due_week,
           coalesce(s.delivered_at > o.promised_at, true) AS is_late   -- не доставлен к сроку = опоздал
    FROM orders o
    JOIN suppliers sp ON sp.id = o.supplier_id
    LEFT JOIN shipments s ON s.order_id = o.id
    WHERE o.status IN ('PAID', 'SHIPPED', 'DELIVERED')
      AND o.promised_at < timestamptz '2025-10-01'
      AND sp.integration_type IN ('api', 'sftp')
)
SELECT due_week,
       round(100.0 * avg(is_late::int) FILTER (WHERE integration_type = 'api'), 1)  AS api_late_pct,
       round(100.0 * avg(is_late::int) FILTER (WHERE integration_type = 'sftp'), 1) AS sftp_late_pct,
       count(*) FILTER (WHERE integration_type = 'sftp') AS sftp_orders
FROM due
GROUP BY due_week
ORDER BY due_week;
```

```

------------+--------------+---------------+-------------
 2025-03-31 |         10.0 |          35.9 |         765
 2025-04-07 |          8.0 |          34.2 |        1202
 ...
 2025-07-07 |          8.4 |          34.7 |        1178
 2025-07-14 |          8.1 |          42.1 |        1213
 2025-07-21 |          8.2 |          32.9 |        1412
 ...
 2025-09-22 |          8.7 |          34.9 |        2642
 2025-09-29 |          9.1 |          30.7 |         742
```

Устойчивая картина: у api около 8%, у sftp около трети. Выброс недели 14 июля — следствие пяти дней без фида у поставщика 31 из задачи 2: его заказы, созданные 8–15 июля, опоздали все. Последняя строка — неполная неделя (два дня), её стоит пометить.

Решения, которые нужно записать: заказы с `promised_at IS NULL` (апрельские заказы канала `api`; всего их около 590, в эту выборку из них попали бы около 500) выпали из выборки — сказать это явно; отменённые не считаются; неделя — ISO, с понедельника (`date_trunc('week', ...)`). `avg(bool::int)` — короткая запись доли; `::int` — специфика PostgreSQL, переносимо — `avg(CASE WHEN ... THEN 1.0 ELSE 0 END)`.

### Задача 4. Поставщик с систематическим сдвигом времени

Сравните время отгрузки по журналу статусов (`order_status_history`, событие `SHIPPED`) и по `shipments.shipped_at`. Найдите поставщика с систематическим сдвигом, величину сдвига и проверьте, затрагивает ли он другие события этого поставщика. Таймер: 20 минут.

<details markdown="1">
<summary>Решение и разбор</summary>

```sql
WITH hist_shipped AS (
    SELECT order_id, min(changed_at) AS shipped_at_hist
    FROM order_status_history
    WHERE status = 'SHIPPED'
    GROUP BY order_id
)
SELECT o.supplier_id,
       count(*) AS orders,
       min(h.shipped_at_hist - s.shipped_at) AS min_diff,
       max(h.shipped_at_hist - s.shipped_at) AS max_diff,
       count(*) FILTER (WHERE h.shipped_at_hist <> s.shipped_at) AS mismatched
FROM shipments s
JOIN hist_shipped h ON h.order_id = s.order_id
JOIN orders o ON o.id = s.order_id
GROUP BY o.supplier_id
HAVING count(*) FILTER (WHERE h.shipped_at_hist <> s.shipped_at) > 0;
```

```
 supplier_id | orders | min_diff  | max_diff  | mismatched
-------------+--------+-----------+-----------+------------
          33 |   3672 | -03:00:00 | -03:00:00 |       3672
```

`min = max = −3 часа` и расходятся все заказы поставщика — это не задержка, а пояс: система поставщика пишет московское время с пометкой UTC. Проверка на событиях `DELIVERED` того же поставщика (сравнение с `shipments.delivered_at`) даёт тот же −3 часа у всех ~3600 доставленных. Внешний симптом — около сотни заказов, «отгруженных раньше оплаты»:

```sql
WITH ev AS (
    SELECT order_id,
           min(changed_at) FILTER (WHERE status = 'PAID')    AS paid_at,
           min(changed_at) FILTER (WHERE status = 'SHIPPED') AS shipped_at
    FROM order_status_history
    GROUP BY order_id
)
SELECT o.supplier_id, count(*) AS shipped_before_paid
FROM ev
JOIN orders o ON o.id = ev.order_id
WHERE ev.shipped_at < ev.paid_at
GROUP BY o.supplier_id;
-- 33 | 112
```

Ловушка: соединить `shipments` с журналом без `min()` — у каждого 50-го заказа событие `SHIPPED` записано дважды, и расхождений станет больше (около 6400 строк вместо 3672) за счёт размножения строк, а не сдвига. Что делать: зафиксировать, какой источник — эталон времени отгрузки, и попросить исправить запись у поставщика или нормализовать время при загрузке.

</details>

### Задача 5. Активация по месяцу регистрации и сегменту

Посчитайте долю активированных покупателей (первый заказ в течение 14 дней после регистрации) по месяцу регистрации и сегменту (`B2B`, `B2C`). Включите только тех, по кому вывод можно сделать честно. Таймер: 15 минут.

<details markdown="1">
<summary>Решение и разбор</summary>

```sql
WITH first_order AS (
    SELECT customer_id, min(created_at) AS first_order_at
    FROM orders
    GROUP BY customer_id
),
eligible AS (            -- окно активации целиком внутри периода данных
    SELECT id, segment, registered_at
    FROM customers
    WHERE registered_at >= timestamptz '2025-04-01'
      AND registered_at <  timestamptz '2025-10-01' - interval '14 days'
)
SELECT date_trunc('month', e.registered_at)::date AS reg_month,
       e.segment,
       count(*) AS registered,
       count(*) FILTER (WHERE f.first_order_at < e.registered_at + interval '14 days') AS activated,
       round(100.0 * count(*) FILTER (WHERE f.first_order_at < e.registered_at + interval '14 days')
             / count(*), 1) AS activation_pct
FROM eligible e
LEFT JOIN first_order f ON f.customer_id = e.id
GROUP BY 1, 2
ORDER BY 2, 1;
```

```
 reg_month  | segment | registered | activated | activation_pct
------------+---------+------------+-----------+----------------
 2025-04-01 | B2B     |        442 |       333 |           75.3
 ...
 2025-09-01 | B2B     |        247 |       193 |           78.1
 2025-04-01 | B2C     |       1826 |      1092 |           59.8
 ...
 2025-09-01 | B2C     |        975 |       742 |           76.1
```

У B2B активация ровная, около 75%; у B2C растёт с 60% до 75–76%. Две отсечки: слева (заказы в базе с 1 апреля — у зарегистрированных в январе–феврале активация была бы 0%) и справа (у зарегистрированных после 17 сентября окно не закрыто — без отсечки сентябрь проваливается до 65%). Сентябрьская когорта поэтому неполная по численности — это надо подписать в отчёте. `LEFT JOIN` обязателен: без него не купившие пропадут из знаменателя и активация станет 100%. Повторные регистрации (одни и те же email с разным регистром) в этой задаче завышают знаменатель: из 150 повторных регистраций в окно отсечки попадают около 90; дедупликация — тема [В.4](v4-window-functions.md).

</details>

### Задача 6. Когортная таблица удержания с отсечкой

Постройте таблицу удержания: строки — месяц первого неотменённого заказа, столбцы `m1`…`m5` — доля когорты, сделавшей хотя бы один неотменённый заказ в соответствующем месяце жизни. Ячейки, месяц которых ещё не закончился к 1 октября, должны быть пустыми. Таймер: 25 минут.

<details markdown="1">
<summary>Решение и разбор</summary>

```sql
WITH monthly AS (           -- покупатель × месяц, в котором был хотя бы один заказ
    SELECT DISTINCT customer_id, date_trunc('month', created_at)::date AS month
    FROM orders
    WHERE status <> 'CANCELLED'
      AND created_at < timestamptz '2025-10-01'
),
cohort AS (
    SELECT customer_id, min(month) AS cohort_month
    FROM monthly
    GROUP BY customer_id
),
cells AS (
    SELECT c.cohort_month,
           ((extract(year FROM m.month) - extract(year FROM c.cohort_month)) * 12
             + extract(month FROM m.month) - extract(month FROM c.cohort_month))::int AS month_n,
           count(*) AS active
    FROM monthly m
    JOIN cohort c USING (customer_id)
    GROUP BY 1, 2
),
complete_cells AS (         -- отсечка: месяц жизни закончился до даты отчёта
    SELECT cl.*,
           first_value(active) OVER (PARTITION BY cohort_month ORDER BY month_n) AS cohort_size
    FROM cells cl
    WHERE cl.cohort_month + make_interval(months => cl.month_n + 1) <= date '2025-10-01'
)
SELECT cohort_month, cohort_size,
       round(100.0 * max(active) FILTER (WHERE month_n = 1) / cohort_size, 1) AS m1,
       round(100.0 * max(active) FILTER (WHERE month_n = 2) / cohort_size, 1) AS m2,
       round(100.0 * max(active) FILTER (WHERE month_n = 3) / cohort_size, 1) AS m3,
       round(100.0 * max(active) FILTER (WHERE month_n = 4) / cohort_size, 1) AS m4,
       round(100.0 * max(active) FILTER (WHERE month_n = 5) / cohort_size, 1) AS m5
FROM complete_cells
GROUP BY cohort_month, cohort_size
ORDER BY cohort_month;
```

```
 cohort_month | cohort_size |  m1  |  m2  |  m3  |  m4  |  m5
--------------+-------------+------+------+------+------+------
 2025-04-01   |        5920 | 77.8 | 70.1 | 66.4 | 64.2 | 60.5
 2025-05-01   |        2025 | 78.6 | 71.2 | 69.6 | 66.0 |
 2025-06-01   |        1799 | 86.5 | 77.3 | 72.3 |      |
 2025-07-01   |        1883 | 89.4 | 83.6 |      |      |
 2025-08-01   |        1921 | 94.6 |      |      |      |
 2025-09-01   |        1535 |      |      |      |      |
```

Ячейка (когорта, месяц жизни `n`) полная, если месяц `cohort_month + n` закончился, то есть `cohort_month + (n + 1) месяцев <= дата отчёта`. Сентябрьская когорта целиком состоит из пустых ячеек: её первый месяц жизни — октябрь. Если вместо отсечки взять `count(DISTINCT ...) / ...` по всем ячейкам, пустые станут нулями и визуально «обрушат» удержание свежих когорт.

Размер когорты взят из ячейки `month_n = 0` через `first_value` — это приём из В.4. Апрельская когорта (около 5900) втрое больше остальных: в ней все, кто купил в апреле впервые *в данных*, включая зарегистрированных в январе–марте (таких около 4600). Причина — в данных нет истории до апреля: «первый заказ в данных» у старых покупателей не обязательно первый в жизни (в анализе выживаемости это называют усечением слева, left truncation). Сравнивать её с остальными некорректно — либо пометить, либо строить когорты по месяцу регистрации только для зарегистрированных с апреля. Номер месяца можно получить и через `age()`: `extract(year FROM age(m, c)) * 12 + extract(month FROM age(m, c))` — для первых чисел месяцев результат совпадает. `make_interval` — специфика PostgreSQL, в стандартном SQL — `(n + 1) * INTERVAL '1' MONTH`; `FILTER` есть в стандарте, но поддерживается не везде, переносимый вариант — `CASE` внутри агрегата.

</details>
